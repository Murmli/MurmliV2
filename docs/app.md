- Gemeinsame ID: `local` und `development` nicht nebeneinander installierbar, `production` schon.
- `local` braucht `aspire run` ([AGENTS.md](../AGENTS.md#aspire-und-azure)), nur für Simulator bzw. Emulator, Geräte nutzen `development`.
- Ab targetSdk 37 (Android 17, heute Flutters Standard 36) braucht `local` für `10.0.2.2` die [Local network permission](https://developer.android.com/privacy-and-security/local-network-permission).
- `development` nutzt für `auth` die Standard-Domain der Container-Apps-Umgebung, nach deren Neuanlage `AppEndpoints` und Tabelle anpassen. Die API läuft unter `api.dev.murmli.de`, nach einer Neuanlage braucht sie die Schritte aus [azure.md](azure.md#custom-domain) und den Namen des neuen Managed Certificate in `api-certificate-name`.
- `production` hat bis zum Release weder Adressen noch Google-Client (`_googleServerClientIdOf`), Lesen wirft `UnimplementedError` (gewollt ungeprüft bei Start und Build).
- Flavor-Namen klein und ohne `-`, weil Flutter auf iOS den Teil nach `-` im Configuration-Namen nimmt und `flavorProvider` per `byName` auf `Flavor` abbildet.

## Starten und Bauen

- Xcode-Scheme `Runner` hat keinen Flavor: `appFlavor` käme aus der zuletzt von der CLI geschriebenen, meist leeren `ios/Flutter/Generated.xcconfig` (`flavorProvider` wirft beim Start `StateError`).
- Nur Swift Package Manager. CocoaPods-Plugins bräuchten im Podfile die Zuordnung jeder Flavor-Configuration (`'Debug-local' => :debug`, `'Profile-local' => :release`, `'Release-local' => :release`).

Beide aus `murmli_icon.vectorcraft` (VectorCraft) exportiert, SVG ohne `<style>` (verwirft das Tool still).
- Jeder `<path>` der Quellen bleibt unter 32.767 Zeichen (derzeit Hut, Hutband, Körper samt Löchern): Längere `pathData` ersetzt aapt2 still durch `STRING_TOO_LARGE`, Android zeigt dann für Icon und Splash sein Standard-Icon (Raster mit Android-Kopf). Prüfen per `aapt2 dump xmltree --file res/drawable/ic_launcher_foreground.xml <apk>`.
- Splash: Orange mit weißem Hamster auf Android und iOS, für alle Flavors gleich (Flavor-Einträge mit `splash: null` unter `android` und `ios`).

Neu erzeugen (in `src/app`, nach Änderungen an Config oder Quellen):

```sh

fvm dart run flutter_adaptive_studio generate
fvm dart run flutter_adaptive_studio generate --flavor local
fvm dart run flutter_adaptive_studio generate --flavor development
rm lib/fas_splash.g.dart ios/Runner.xcodeproj/project.pbxproj.bak
```

- dev_dependency mit fester Version (ohne `^`): nur gezielt erhöhen und dann die Ausgabe prüfen, das Paket ändert sich schnell.
- Ohne `--flavor` schreibt das Tool nach `src/main` bzw. `AppIcon`, ein Flavor-Lauf nur in seinen Overlay bzw. `AppIcon-<flavor>` samt `project.pbxproj`.
- `lib/fas_splash.g.dart` (In-App-Splash, ungenutzt) entsteht bei jedem Lauf mit Splash, `project.pbxproj.bak` bei jedem Flavor-Lauf: beide löschen.
- Optional `fvm dart run flutter_adaptive_studio preview` für eine Vorschau der Masken, schreibt `flutter_adaptive_studio/preview/icon_preview.html`, danach den Ordner löschen.
- Fallen Quellen oder Optionen weg, löscht das Tool nicht alles: vorher zurücksetzen (im Repo-Root `git restore --staged --worktree -- src/app/android src/app/ios` und `git clean -fd -- src/app/android src/app/ios`, löscht auch ungetrackte Nicht-Icon-Dateien dort).
- `FileSystemException` mit errno 1224: Ein anderer Prozess (meist VS Code) hält eine erzeugte Datei offen, schließen und wiederholen.
- Neuer Flavor: Eintrag unter `flavors` (mit `play_store: false` und `splash: null` unter `android` und `ios`) und `generate --flavor <flavor>`.

## API-Zugriff

- `AccessTokenInterceptor` setzt das JWT (`SignedInAccount.accessToken`) nur bei Requests an die `origin` der eigenen API. Erneuert wird 1 Minute vor Ablauf, die Gültigkeit (`exp` minus `iat`) zählt ab Empfang. Parallele Requests teilen eine Erneuerung.
- Antwortet die API mit 401, erneuert der Interceptor das JWT und wiederholt den Request einmal. Ohne Session (nie angemeldet oder `auth` lehnt die Session mit 401 ab, dann ist der Nutzer abgemeldet) bricht er Requests ohne Fehlerdialog ab (`DioExceptionType.cancel`). Ist `auth` nicht erreichbar, scheitert der Request mit Fehlerdialog, die Session bleibt. Der Request erreicht die API dann nie: Zum Support-Code gibt es keinen Trace im Backend, nur die Logzeile der App.
- Wiederholt wird nur unter der Session, die das abgelehnte JWT ausgestellt hat (`SignedInAccount` merkt sich die JWTs der laufenden Session). Lehnt die API einen Request ab, der vor einem Abmelden oder Kontowechsel losging, bricht der Interceptor ihn ab (`DioExceptionType.cancel`), statt ihn mit dem JWT der neuen Session zu wiederholen.
- Pfade ab `/`, da dio sie als Text an die `baseUrl` (ohne `/` am Ende) hängt: sonst falscher Host (`development`) bzw. ungültiger Port (`local`). Volle URLs ignorieren die `baseUrl`, daher `origin`- statt Instanz-Vergleich.
- `ApiTraceInterceptor` gibt nur Requests an die eigene API einen neuen `traceparent`, auch bei geteilter Instanz. Die API setzt ihn fort ([telemetry.md](telemetry.md#entscheidungen)).
- Request-Logs ohne Bodies (Gesundheitsdaten), Header (Token) und Query (Nutzereingaben). Den `DioException`-Text, den `main.dart` und Sentry melden, ersetzt `ApiTraceInterceptor` durch seine Logzeile: dios Text kann URL samt Query (`HttpException`) oder Body-Teile (`FormatException`) enthalten.
- Fehlerdialog (`ApiErrorDialogListener`): höchstens einer gleichzeitig, keiner bei Abbruch per `CancelToken`, unsichtbarer App oder fehlendem Navigator (auch nicht nachträglich). Aufrufer erhalten den Fehler trotzdem.
- Requests im Hintergrund, etwa der Abgleich, setzen `extra: {unreportedFailureKey: true}` (`api_client_provider.dart`): Ihr Fehler bekommt keinen Fehlerdialog, geloggt wird er trotzdem.
- dio ruft auch `onError` in Interceptor-Reihenfolge auf, `handler.resolve` überspringt die folgenden: Als erster loggt `ApiTraceInterceptor` jeden Request, als letzte lässt die Meldung an `failedApiRequestTraceIdProvider` selbst behobene Fehler ohne Dialog.
- `android.permission.INTERNET` im Haupt-Manifest gibt Release-Builds Netz, Flutters Vorlagen-Kopien unter `debug` und `profile` bleiben.

## Lebenszyklus und Netz

- Ob die App im Vordergrund ist, liefert `appForegroundProvider` (`lib/app/core/lifecycle/app_foreground_provider.dart`) aus einem `AppLifecycleListener`: `resumed` und `inactive` (etwa Kontrollzentrum oder Anruf) gelten als Vordergrund, `hidden`, `paused` und `detached` als Hintergrund, ohne bekannten Zustand Vordergrund. `ApiErrorDialogListener` prüft die Sichtbarkeit beim Anzeigen weiter direkt.
- Den Netzstatus liefert `networkAvailableProvider` (`lib/app/core/network/network_available_provider.dart`) aus `connectivity_plus`: `true`, solange das System irgendein Netz meldet, und bis zur ersten Meldung. Den Anfangszustand liest er per `checkConnectivity`, weil Android ohne Netz beim Start nichts meldet; eine Meldung aus dem Strom gewinnt. Der Status ist nur ein Hinweis (ein WLAN hinter einem Captive Portal gilt als Netz), maßgeblich bleibt, ob Requests gelingen; kein Request wartet auf ihn. `connectivity_plus` braucht keine Einrichtung im Projekt: Die Berechtigung `ACCESS_NETWORK_STATE` bringt das Plugin in seinem Android-Manifest mit, iOS braucht nichts.
- Der Abgleich nutzt beide ([sync.md](sync.md#steuerung-der-runden)). Tests überschreiben die Provider per `overrideWithBuild` und setzen `state`, nie über Plattform-Channels; `appForegroundProvider` selbst prüft ein Widget-Test, der Zustände per `changeLifecycleState` (`test/helpers/lifecycle.dart`) sendet.

## Anmeldung

Die Onboarding-Seite ist die Anmeldeseite (kein Onboarding-Flag), Optionen je Flavor und Plattform (`SignInOptions`):

- `local`: nur E-Mail und Passwort, Test-Nutzer: [authentication.md](authentication.md#nutzer-anlegen).
- `development`, `production`: Apple nur auf iOS (`SignInWithAppleButton`), Google nur auf Android (eigener Button, [Entscheidungen](#entscheidungen)), kein Formular.

Ablauf: [authentication.md](authentication.md#anmeldung). `signedInAccountProvider` hält das Konto, ohne Konto leitet `SignInGuard` jede geschützte Route zur Onboarding-Seite.

- Apple bekommt den SHA-256 eines zufälligen Nonce, `auth` den rohen.
- Google: nativer Dialog des Button-Ablaufs (`GetSignInWithGoogleOption`, nicht Bottom Sheet), Initialisierung einmal pro Prozess.
- Abbruch im Dialog von Apple oder Google zeigt nichts. Bei Google kommt auch ein falscher SHA-1 oder Paketname (etwa jeder Debug-Build) nach der Kontoauswahl als Abbruch an, für das Plugin ununterscheidbar vom Nutzer-Abbruch ([authentication.md](authentication.md#sign-in-with-google)).
- Die Anmeldung überdauert Neustarts in genau einem Eintrag `session` im Secure Storage (`flutter_secure_storage`) mit Session-Token und Konto-Id. Auf iOS mit `first_unlock_this_device`: Spätere Hintergrundarbeit kann ihn nach dem ersten Entsperren lesen, `_this_device` hält ihn aus Backups. Das JWT liegt nur im Speicher.
- Installationsmarke `installed` in den SharedPreferences: Fehlt sie, leert `restore()` den Secure Storage, weil die iOS-Keychain eine Deinstallation überdauert.
- Android: Der Keystore-Schlüssel kommt nie ins Auto Backup. Nach einer Wiederherstellung löscht `resetOnError` die unlesbaren Daten, der Nutzer ist abgemeldet.
- `main.dart` ruft `restore()` ohne Netz auf, die Session prüft danach eine JWT-Anfrage im Hintergrund. Lehnt `auth` sie mit 401 ab, ist der Nutzer abgemeldet (kurz sichtbare Startseite möglich), andere Fehler lassen ihn angemeldet. So öffnet die App auch offline und während des Kaltstarts von `auth`.
- Scheitert die Anmeldung, nachdem `auth` die Session angelegt hat (JWT, `/v1/users/me` oder Secure Storage), beendet die App sie im Hintergrund bei `auth` (`POST /api/auth/sign-out`), Fehler dabei nur im Log.
- Abmelden (Einstellungen › Konto) beendet zuerst die Session bei `auth` (`POST /api/auth/sign-out` mit dem Session-Token). Ist `auth` nicht erreichbar, bestätigt der Nutzer das Abmelden nur auf dem Gerät, die Session am Server läuft dann nach 30 Tagen ohne Nutzung ab. Kann das Gerät die gespeicherte Session weder löschen noch überschreiben, scheitert das Abmelden nur auf dem Gerät mit einem Popup und der Nutzer bleibt angemeldet.
- Konto löschen (Einstellungen › Konto, `AccountActions.delete`) fragt nach einer Bestätigung und sendet `DELETE /v1/users/me`, die Löschung im Backend beendet auch die Sessions bei `auth`. Danach beendet die App die Session wie beim Abmelden, entfernt alle Daten vom Gerät und zeigt auf iOS den Hinweis zu Sign in with Apple (siehe unten). Scheitert der Request, zeigt `apiClientProvider` den allgemeinen Fehlerdialog, der Nutzer bleibt angemeldet und kann es erneut versuchen.
- Auf dem Gerät bleiben nur das Opt-out der Absturzberichte und die Installationsmarke: Das Opt-out ist eine Entscheidung für das Gerät, die auch vor der Anmeldung gilt, die Marke braucht `restore()`, um eine Neuinstallation zu erkennen und den Secure Storage zu leeren.
- Geht die Antwort auf die Löschung verloren, scheitert der erneute Versuch an der Token-Erneuerung: `auth` lehnt die Session mit 401 ab, die Session endet und die App entfernt die Daten vom Gerät wie nach einer erfolgreichen Löschung (`AccountDeletionResult.sessionEnded`).
- Entscheidung: Ein 401 beim Start (`_checkRestoredSession`) meldet nur ab und lässt die Daten auf dem Gerät, weil sich dort ein gelöschtes Konto nicht von einer abgelaufenen Session unterscheiden lässt.
- Nach der Löschung zeigt die App auf iOS außerhalb von `local` immer den Hinweis, die Verbindung zu Sign in with Apple in den iPhone-Einstellungen zu trennen (`AppleDisconnectNoticeListener`, über der Onboarding-Seite), weil Better Auth das Token bei Apple derzeit nie widerruft. [#51](https://github.com/Murmli/MurmliV2/issues/51) stellt ihn auf ein Feld der Antwort um, das einen gescheiterten Widerruf meldet.
- Ein Listener in `MurmliApp` führt bei jedem Wechsel von angemeldet zu abgemeldet von jeder Seite zur Onboarding-Seite.
- Sign in with Apple braucht ein Gerät mit Apple Account mit Zwei-Faktor-Authentifizierung, im Simulator unzuverlässig (Apple-Feedback FB25318712).
- Offen bis zum Release: `sign_in_with_apple` 8.2.0 scheitert auf dem iPad mit Fehler 1000 ([aboutyou/dart_packages#489](https://github.com/aboutyou/dart_packages/issues/489)).

## Lokale Datenbank

- drift (`drift_flutter`), eine Datenbank `AppDatabase` (`src/app/lib/app/core/database/app_database.dart`), nur über `appDatabaseProvider`. Die Datei `murmli.sqlite` liegt im Ordner `local-data` des Application-Support-Verzeichnisses.
- `local-data` ist von den Sicherungen des Systems ausgenommen: auf Android per `res/xml/backup_rules.xml` (bis Android 11) und `res/xml/data_extraction_rules.xml` (Cloud-Sicherung und Gerätewechsel), auf iOS per `isExcludedFromBackup`, gesetzt über den Channel `de.murmli.app/backup` aus `AppDelegate.swift` bei jedem Öffnen. Scheitert das auf iOS, öffnet die Datenbank trotzdem, mit Warnung im Log. Die Daten gehören zum angemeldeten Konto und kommen später vom Server.
- Alle Tabellen liegen unter `src/app/lib/app/core/database/tables/`, auch die eines Features (`core/database` importiert nichts aus `features/`). Zeilenklassen heißen `<Name>Row` (`@DataClassName`), damit sie nicht mit den Domänenmodellen kollidieren. Fremdschlüssel gelten (`PRAGMA foreign_keys = ON` in `beforeOpen`).
- Tabellen des Abgleichs (`tables/sync_tables.dart`): `sync_commands` (Warteschlange), `sync_states` (eine Zeile mit `id` 1: Konto, Gerät, Token, Grenzen des Servers, `local_state_generation`), `sync_scopes`, `sync_members` und `sync_notices`. Sie schreibt nur der Sync-Kern ([sync.md](sync.md#kern-der-app)).
- Lokale Daten löscht nur der Sync-Kern (`SyncCore.adoptAccount`, [sync.md](sync.md#konto-der-app)): Ohne angemeldetes Konto leert er alle Tabellen (`allTables`) samt den Tabellen der Datentypen in einer Transaktion, beim Abmelden, beim Abmelden nur auf dem Gerät, bei einer von `auth` abgelehnten Session, nach 410 `account-gone` und beim Start ohne Anmeldung, ebenso vor dem Übernehmen der Daten eines anderen Kontos. Nur `local_state_generation` in `sync_states` überdauert, erhöht, damit eine Antwort auf eine Anfrage von vorher nicht mehr gilt. `main.dart` liest `syncCoreProvider` nach `restore()`, sonst löschte die erste Meldung ohne Konto die Daten eines angemeldeten Nutzers.
- IDs erzeugt `newUuid()` (`src/app/lib/app/core/identifiers/new_uuid.dart`, UUID v4 aus einem kryptografischen Zufallsgenerator) auf dem Gerät, damit der Abgleich sie ohne Umschlüsseln übernimmt.

### Schema-Versionen

- Jede Änderung an den Tabellen von `AppDatabase` bekommt eine neue `schemaVersion`. drift_dev hält den Stand jeder Version als Dump in `src/app/drift_schemas/app_database/drift_schema_v<n>.json` (Konfiguration in `build.yaml`). Version 1 sind die Tabellen der Einkaufsliste, Version 2 ergänzt die Tabellen des Abgleichs.
- Ablauf: Tabellen ändern, `schemaVersion` erhöhen, `fvm dart run drift_dev make-migrations`, den Step in `migrationSteps` schreiben, den Test mit Daten in `test/drift/app_database/migration_test.dart` ergänzen, `fvm flutter test test/drift test/app/core/database` ausführen. Commit samt Dump, `lib/app/core/database/app_database.steps.dart` und allem unter `test/drift/` (Ausgabe des Generators, nie von Hand ändern; nur `migration_test.dart` schreibt er einmalig und lässt es danach in Ruhe, Tests mit Daten gehören dort hinein).
- `onUpgrade` in `AppDatabase` folgt für `from < to` dem Ablauf der [drift-Doku](https://drift.simonbinder.eu/migrations/): `PRAGMA foreign_keys = OFF`, `migrator.runMigrationSteps` mit `migrationSteps(from1To2: …, …)` und je Step einer Transaktion, danach muss `PRAGMA foreign_key_check` leer sein (sonst `StateError`, in jedem Build statt nur unter `kDebugMode`), dann `PRAGMA foreign_keys = ON`.
- Nach jedem Upgrade verwirft die Migration das Token des Abgleichs und erhöht `local_state_generation`: Die neue Version kann Datentypen oder Felder kennen, die das alte Token nie geholt hat, die nächste Runde holt deshalb einmal den vollständigen Stand. Beim Upgrade von Version 1 gibt es noch keine Zeile in `sync_states`. Einen Test dafür gibt es erst mit dem ersten Step ab Version 2 ([#142](https://github.com/Murmli/MurmliV2/issues/142)), er prüft dann in `test/app/core/database/app_database_test.dart` Token und Generation auf dem Weg von Version 2 zur neuesten (dieser Satz entfällt dann).
- Die Warteschlange (`sync_commands`) übersteht jede Migration: Ein Step ändert oder löscht die Tabelle nie, ohne die wartenden Kommandos zu übernehmen.
- Downgrade (eine Datenbank einer höheren Version, etwa nach dem Wechsel auf einen älteren Build): Die Migration löscht alle Tabellen der Datei, auch die der neueren Version unbekannten, und legt das Schema neu an ([Entscheidungen](#entscheidungen)).
- Die CI (Job App in `lint.yml`) führt `make-migrations` aus und scheitert, wenn sich danach etwas unter `drift_schemas`, `test/drift` oder `lib/app/core/database` ändert oder neu entsteht (vergessener Dump). Geänderte Tabellen ohne neue `schemaVersion` lässt schon `make-migrations` scheitern, weil der Dump der Version abweicht.

## Einkaufsliste

- Tabellen (`tables/shopping_list_tables.dart`): `shopping_lists` (ID, Name), `shopping_list_items` (ID, `scope_id` mit der ID der Liste ohne Fremdschlüssel, Name, Menge und Einheit optional, Kategorie, abgehakt, Sprache der App beim Anlegen, `created_at` und `changed_at` in Millisekunden), lokal `shopping_list_item_recipes` (Rezeptanteile je Artikel und Rezept mit Titel und Menge in der Einheit des Artikels, `ON DELETE CASCADE` am Artikel) und `shopping_category_positions` (Kategorie-Reihenfolge je Person, leer heißt Standardreihenfolge). Die Artikel haben schon die Form des Abgleichs ([#142](https://github.com/Murmli/MurmliV2/issues/142)).
- Feste Schlüssel: `MarketCategory` (22, in der Standardreihenfolge) und `MeasurementUnit` (11) speichern `key` in camelCase, nie Enum-Namen oder Positionen. Sie entsprechen `src/sync-cases/shopping/catalog.json` des Backends und ändern sich nur gemeinsam mit ihm. Unbekannte Schlüssel lesen sich als `miscellaneous` bzw. ohne Einheit. Bezeichnungen per slang unter `shoppingList.categories` und `shoppingList.units`.
- Modelle (`features/shopping_list/models/`, dart_mappable): `ShoppingList` mit den Artikeln nach Anlage und ID, `ShoppingListItem` mit `recipeShares` und `ownQuantity` (Menge minus Rezeptanteile, nie unter 0, ohne Menge `null`), `RecipeShare`.
- `ShoppingListRepository` (`shoppingListRepositoryProvider`, auf drift `DriftShoppingListRepository`) liest die Liste und die Kategorie-Reihenfolge (immer alle 22, gespeicherte zuerst) als Stream und schreibt jede Änderung in einer Transaktion, Zeiten aus `appClockProvider`. Rezept-Artikel entfernen lässt Artikel mit eigenem Anteil mit genau diesem ohne Rezepte stehen. Das Übernehmen von Rezeptzutaten kommt mit dem Planer.
- Nach der Anmeldung legt `firstShoppingListProvider` die Liste an, wenn keine besteht (Name leer). Nur in Debug-Builds und im Flavor `local` füllt er sie mit Beispieldaten (`sample_shopping_list.dart`, Namen in der Sprache der App, Rezeptanteile direkt über die Datenbank). In Debug-Builds setzt ein Knopf im Tab „Kalorien“ sie zurück, solange der Tab ein Platzhalter ist.
- Ansicht (Tab „Liste“, `ShoppingListPage`): `shoppingListOverviewProvider` fasst die Liste (`currentShoppingListProvider`) und die gespeicherte Kategorie-Reihenfolge (`marketCategoryOrderProvider`) zusammen, bis beide da sind `null` (Ladeanzeige). Gruppen je Kategorie in dieser Reihenfolge, nur Kategorien mit offenen Artikeln, darin nur die offenen Artikel in der Reihenfolge der Liste. Die Seite zeigt ihren Kopf selbst (`HomeTab.rendersOwnHeader`, derselbe `HomeHeader` wie auf der `HomePage`) und ist eine einzige `CustomScrollView`, auch im leeren Zustand: Der Kopf (`SliverFloatingHeader`) scrollt beim Herunterscrollen weg und kommt beim Zurückscrollen wieder, das Eingabefeld darunter (`PinnedHeaderSliver`) bleibt oben stehen. Jede Gruppe (`ShoppingListGroupSliver`, auf der Seite nach Kategorie geschlüsselt) und der Bereich „Abgehakt“ sind eine `ShoppingListSection` (ein `SliverMainAxisGroup`), deren Überschrift (`ShoppingListPinnedHeader`, fester `SliverPersistentHeader` in der Hintergrundfarbe mit der Höhe aus Zeilenhöhe der Textstile samt Textskalierung) oben stehen bleibt, bis die nächste Gruppe sie hinausschiebt. Der Fortschritt zählt alle Artikel samt abgehakten und erscheint nur bei mindestens einem Artikel, als Pille „2 / 16“ rechts im Eingabefeld vor dem runden Knopf (`ShoppingListProgressCounter`, vorgelesen als „2 von 16 erledigt“), umrandet von einem Fortschrittsrahmen, der oben in der Mitte beginnt und im Uhrzeigersinn wächst. Ist der Text breiter als die Höchstbreite der Pille (etwa bei großer Schrift), entfallen die Leerzeichen („2/16“). Sobald im Feld Text steht, verschwindet die Pille. Der Kopf zeigt nur Titel und den Knopf des Optionsmenüs. Abgehakt und wieder geöffnet wird nur über die Kachel (`ShoppingListItemRow`, Tap-Fläche 48 breit über die volle Zeilenhöhe), ein Tap auf den Rest der Zeile öffnet das Artikelmenü. Der Tap auf die Kachel speichert die Änderung sofort. Der Artikel erscheint aufklappend in seinem neuen Bereich (`recentlyToggledItemProvider` merkt sich den Artikel, damit nur dessen neue Zeile aufklappt, nicht beim Abhaken in den eingeklappten Bereich „Abgehakt“) und blendet gleichzeitig an seinem alten Platz aus und klappt zusammen: `leavingShoppingListItemsProvider` hält ihn im Stand vor dem Tap, bis diese Zeile verschwunden ist, `shoppingListOverviewProvider` setzt ihn dort wieder ein (`leavingItemIds` der Gruppe bzw. `leavingCheckedItemIds`). Verlässt der letzte Artikel eine Gruppe bzw. den Bereich „Abgehakt“, klappt der ganze Bereich samt Überschrift zusammen und blendet aus; kommt der erste Artikel per Abhaken oder Öffnen hinzu, klappt er samt Überschrift auf (`ShoppingListSection`), nicht beim Aufbau der Seite und nicht beim Hinzufügen über das Eingabefeld. Hat ein Bereich nur einen Artikel, animiert der Bereich statt dessen Zeile (`animatesWithSection`), die Zeile entfernt ihren Eintrag in `leavingShoppingListItemsProvider` trotzdem selbst am Ende. Beim Einklappen von „Abgehakt“ entfernt `checkedSectionExpandedProvider` die abgehakten Einträge daraus, weil deren Zeilen nicht mehr gebaut werden. Alle Zahlen (Fortschritt, Gruppen, „Abgehakt“, Hinweis bei allen abgehakten) zählen nur die gespeicherten Artikel. Jede Zeile außer der ersten ihres Bereichs trägt ihre Trennlinie selbst, die mit ihr zusammenklappt. Bei reduzierter Bewegung ohne Animation. Abgehakte Artikel stehen unten im Bereich „Abgehakt“ (`ShoppingListCheckedSectionSliver`), zuletzt abgehakte zuerst (nach `changedAt`); er lässt sich einklappen, der Zustand bleibt auf dem Gerät (`PreferenceKeys.shoppingListCheckedExpanded`, `checkedSectionExpandedProvider`) und geht mit den übrigen Gerätedaten bei der Kontolöschung. Sind alle Artikel abgehakt, steht ein Hinweis über dem Bereich, der leere Zustand erscheint nur ohne jeden Artikel. Der Knopf „Leeren“ rechts in der Überschrift von „Abgehakt“, auch eingeklappt sichtbar, ist dieselbe Aktion wie „Abgehakte entfernen“ im Optionsmenü; deshalb ist diese Überschrift mindestens 48 hoch (`kMinInteractiveDimension`, sonst auch nach der Zeilenhöhe der Beschriftung des Knopfs). Menge und Einheit formatiert `quantityLabel` (`quantity_label.dart`, Zahl per `NumberFormat('0.###')` von intl in der Sprache der App, Einheit als Abkürzung). Kategorie-Icons sind SVGs unter `src/app/assets/icons/categories/` (eine Datei je `MarketCategory`, Name in snake_case), gezeichnet per flutter_svg in `MarketCategoryTile`; Icon und Farbfamilie je Kategorie stehen nur in `market_category_appearance.dart`. Die Lizenz der Icons klärt [#166](https://github.com/Murmli/MurmliV2/issues/166).
- Artikelmenü und Bearbeiten: Ein Tap auf den Rest der Zeile öffnet das Artikelmenü `showShoppingListItemMenu` (`shopping_list_item_menu.dart`), offen wie abgehakt: im Kopf die Kategorie-Kachel, „Name · Menge“ (ohne Menge nur der Name) und darunter die Kategorie, dann die Einträge „Bearbeiten“, „Alternative finden“, der Rezept-Eintrag (nur mit Rezeptanteilen) und „Löschen“ (rot). Bei genau einem Rezept heißt er „Rezept anzeigen“ mit dem Rezepttitel darunter, bei mehreren „Rezepte anzeigen“ mit ihrer Anzahl: Ein Tap klappt darunter die Rezepte in gespeicherter Reihenfolge auf und wieder zu (anfangs zu, nicht gespeichert). „Alternative finden“ ([#90](https://github.com/Murmli/MurmliV2/issues/90)), „Rezept anzeigen“ und die aufgeklappten Rezepte sind Platzhalter, bis Rezepte mit [#91](https://github.com/Murmli/MurmliV2/issues/91) zu öffnen sind: blasser, mit der Marke „Bald“, deaktiviert und als „bald verfügbar“ vorgelesen. „Bearbeiten“ schließt das Menü und öffnet die Bearbeitung, „Löschen“ schließt es und löscht. Ein langer Druck auf die Zeile öffnet die Bearbeitung `showShoppingListItemEditor` (`shopping_list_item_editor.dart`) direkt: Felder mit Beschriftung darüber, Name in voller Breite, darunter Menge neben der Einheit und der Hinweis „Menge und Einheit dürfen leer bleiben.“ (bei ungültiger Menge an seiner Stelle der Fehler), die Kategorie als Schaltfläche mit Kachel und Namen (Auswahl per `MenuAnchor` in der Kategorie-Reihenfolge), dann „Speichern“ und „Abbrechen“ (schließt ohne Speichern, ebenso das Schließen des Sheets). Einheiten sind Chips: „Stk.“, „g“ und „kg“ stehen fest da, „Mehr“ öffnet die übrigen; eine andere gewählte Einheit erscheint als zusätzlicher gewählter Chip vor „Mehr“, ein Tap auf den gewählten Chip hebt die Auswahl auf (keine Einheit). Der Name ist Pflicht und die Menge größer als 0 oder leer, die Rezeptanteile bleiben unberührt (`updateItem`). Gelöscht wird über „Löschen“ im Artikelmenü oder durch Wischen der Zeile zum Zeilenanfang (`Dismissible`, löscht in `confirmDismiss`, die Zeile verschwindet mit dem nächsten Stand der Liste), jeweils ohne Nachfrage und ohne Rückgängig. Eigene Rezeptlogik beim Bearbeiten kommt erst mit den Rezepten.
- Optionsmenü (`showShoppingListMenu`, `shopping_list_menu.dart`): Bottom Sheet für Aktionen auf der ganzen Liste, geöffnet über den Knopf mit drei Punkten ganz rechts im Kopf der Liste (`HomeHeader.trailing`, ersetzt dort den Knopf der Einstellungen und scrollt mit dem Kopf weg). Titel ist der Titel des Tabs („Einkaufsliste“, Listen haben noch keinen Namen), darunter Abschnitte mit Überschrift in Großbuchstaben (`toUpperCase()` auf dem übersetzten Text): „Aufräumen“ mit „Abgehakte entfernen“ und „Liste leeren“ (rechts die Zahl der betroffenen Artikel als Marke, ohne betroffene Artikel ohne Marke, blasser und ohne Funktion), „Liste“ mit „Kategorien sortieren“, zuletzt ohne Überschrift „Einstellungen“ (dieselbe `SettingsRoute` wie im Kopf der übrigen Tabs). Die Zeilen teilt das Optionsmenü mit dem Artikelmenü (`ShoppingListSheetEntry`, ohne `onTap` deaktiviert). Beide Aufräum-Aktionen fragen vorher nach (`shopping_list_cleanup.dart`): Bei höchstens drei betroffenen Artikeln nennt die Meldung deren Namen in der gespeicherten Reihenfolge der Liste („A“, „A und B“, „A, B und C“, Bindewort aus den Übersetzungen), bei mehr nur die Zahl; der Knopf heißt „N Artikel entfernen“. „Liste leeren“ behält die Kategorie-Reihenfolge. „Rezeptzutaten entfernen“ kommt mit den Rezepten ([#169](https://github.com/Murmli/MurmliV2/issues/169)), das Repository hat dafür schon `deleteRecipeItems`.
- Kategorien sortieren (`CategoryOrderPage`, eigene Route `CategoryOrderRoute`): ohne AppBar, oben ein runder Zurück-Knopf neben dem Titel, darunter ein Hinweis und alle 22 Kategorien ohne Artikel, auch leere, in einer Karte (`DecoratedSliver` um eine `SliverReorderableList` in einer `CustomScrollView`, damit das Ziehen die Seite mitscrollt), verschiebbar per Griff am Zeilenanfang (`ReorderableDragStartListener`) und per Knöpfen nach oben und unten am Zeilenende (auch für Screenreader). Jede Änderung speichert sofort (`setCategoryOrder`), die Seite zeigt bis zum neuen Stand des Streams ihren eigenen. „Standard wiederherstellen“ steht in einer festen Leiste unten, fragt vorher nach (`showConfirmationDialog`) und ist bei Standardreihenfolge aus. Die Reihenfolge gilt je Person, bleibt lokal und wird nicht abgeglichen.
- Eingabe (`ShoppingListEntryField`): Das Feld steht immer über der Liste und bleibt beim Scrollen oben, auch im leeren Zustand. Rechts stehen die Büroklammer („Foto oder Sprachnotiz anhängen“, Platzhalter ohne Funktion für Foto, Sprachnotiz und das Media-Menü, deshalb deaktiviert) und der Senden-Knopf (Tooltip „Hinzufügen“), der bei leerem Feld grau und deaktiviert ist und sich in die Markenfarbe umfärbt, sobald das Feld Text enthält; auch die Aktion der Tastatur schickt ab, Feld und Tastatur bleiben danach offen. Beginnt die Eingabe, gleitet die Pille des Fortschritts zwischen Feld und Knöpfen hinaus; wird das Feld wieder leer, kommt sie zurück, bei reduzierter Bewegung ohne Animation. `pendingShoppingListEntriesProvider.submit` kürzt den Text (leer schickt nichts ab), zeigt ihn bis zum Ende der Verarbeitung als wartenden Eintrag oben in der Liste (`ShoppingListPendingEntries`) und schreibt die Artikel nur, wenn noch dasselbe Konto angemeldet ist wie beim Abschicken. Den Text zerlegt `ShoppingItemParser` (`shoppingItemParserProvider`), derzeit `MockShoppingItemParser` mit vier festen deutschen Eingaben und 900 ms Verzögerung, alles andere wird ein Artikel unter „Verschiedenes“; später übernimmt das die KI-Anbindung. Gleiche Artikel werden noch nicht zusammengeführt ([#165](https://github.com/Murmli/MurmliV2/issues/165)).
- Der Abgleich mit dem Backend ersetzt Beispieldaten und das Anlegen der ersten Liste. Weil die Rezeptanteile mit ihrem Artikel gelöscht werden, muss er Artikel an Ort und Stelle ändern, nie löschen und neu anlegen.

## Absturzberichte (Sentry)

- Organisation `murmli` (EU, `de.sentry.io`), Projekt `app`. Nur Release- und Profile-Builds von `development` und `production` melden, Environment ist der Flavor. DSN pro Flavor im Code (kein Geheimnis).
- Opt-out: Hinweis im Onboarding, Schalter „Fehlerberichte senden“ unter Einstellungen › Datenschutz.
- Fehler vor `CrashReporting.start()` in `main.dart` (nach Talker-Handlern und SharedPreferences) meldet Sentry nicht.
- `SentryFlutter.init` legt seine Handler vor die aus `main.dart` (ruft sie weiter auf), `Sentry.close()` setzt zurück.
- Ausschalten beendet Sentry samt nativen SDKs sofort und löscht ungesendete Berichte ([Entscheidungen](#entscheidungen)), Einschalten startet es neu.
- Wiedereingeschaltet meldet das Android-SDK den letzten ANR der vergangenen 90 Tage (`ApplicationExitInfo`), auch schon gemeldete oder aus der ausgeschalteten Zeit, da die Marke des zuletzt gemeldeten im gelöschten Cache lag.
- Fehler aus `FlutterError.onError` melden zusätzlich Kontext und Diagnose der `FlutterErrorDetails` (`flutter_error_details`), etwa `NetworkImage("<URL>")` mit voller URL.
- Nutzer: vor der Anmeldung die zufällige Installations-ID der nativen SDKs, danach die eigene Konto-Id, gesetzt von `CrashReporting` bei Änderungen von `signedInAccountProvider` und nach jedem Sentry-Start (`Sentry.close()` verwirft den Scope).
- Sitzungen (Release Health) auch ohne Fehler, neu bei jedem Sentry-Start und ab 30 Sekunden im Hintergrund.
- Probleme, die die App selbst behandelt, meldet `CrashReporter.reportProblem` als Exception `ReportedProblem` mit festem Text (beim Abgleich nur die Fälle aus [sync.md](sync.md#telemetrie-der-app), höchstens mit Datentyp, Kommandoart und Grund), nie als Nachricht oder Log.
- Support-Code: in Sentry `api_trace_id:<Support-Code>` suchen. Tag von `ApiTraceIdEventProcessor` für `DioException`s der eigenen API, auch in Riverpods `ProviderException`.

## Tests

- `flutter test` läuft im Debug-Modus ohne `--flavor` (für den Test des Standard-Flavors). Tests setzen `flavor` per `pumpApp` oder `createContainer`, `debugBuild` per `createContainer`, in `CrashReporting`-Tests immer, sonst bliebe der Start auch ohne den geprüften Grund aus.
- `createContainer` (auch in `pumpApp`) nutzt Talker ohne Konsolenausgabe (Logs über `history`). Sentry-Meldungen prüft `startRecordingSentry` (Sentry nur in Dart, Transport zeichnet Envelopes auf).
- `RecordingHttpClientAdapter` ersetzt in Tests den Adapter von `apiClientProvider` und `authClientProvider`. Nur der Test auf fehlende Sentry-Trace-Header nutzt dios echten Adapter mit `HttpOverrides` und `HttpServer` auf Loopback, sonst blieben im Adapter gesetzte Header (etwa von `sentry_dio`) unsichtbar.
- Widget-Tests hängen Erwartungen an Requests per `expectLater` vor `tester.pumpAndSettle()` an, warten danach: dios Timer laufen unter `FakeAsync` nur beim Pumpen. Direkt gewartet hängt der Test, danach angehängt wird der Fehler unbehandelt gemeldet.
- `FakeSignInWithApplePlatform` und `FakeGoogleSignInPlatform` (`installFakeGoogleSignIn`) ersetzen die Dialoge von Apple und Google direkt als `instance` der Plattform-Pakete, ohne eigene Hüllen (wären Test-only-Code). `pumpApp(signedInAccount:)` startet angemeldet über den Secure Storage samt `restore()` wie `main.dart` (mit `respondFromAuth` für die Session-Prüfung), `createContainer(signedInAccount:)` setzt nur das Konto. Den Secure Storage ersetzt `createContainer(secureStorage:)` per `FlutterSecureStorage.setMockInitialValues` in jedem Test, die übergebene Map muss veränderlich sein und zeigt das Gespeicherte, für einen Neustart dieselbe Map erneut übergeben. Requests an die API brauchen eine Session: `signIn` (`test/helpers/authentication.dart`) meldet per E-Mail an, danach setzt der Test seinen Adapter. Die Uhr ersetzt `clock` von `createContainer` (`appClockProvider`).
- `createContainer` (auch in `pumpApp`) gibt jedem Container eine eigene In-Memory-Datenbank (`NativeDatabase.memory()`), die er beim Entsorgen schließt. Eine per `database` übergebene Datenbank schließt der Test selbst, so überdauert sie einen Neustart mit neuem Container. In Widget-Tests laufen Zugriffe auf die Datenbank aus dem Test in `tester.runAsync`, je Aufruf des Repositorys ein eigenes `runAsync` mit anschließendem `pumpAndSettle` (mehrere Schreibvorgänge in einem hängen). Taps im UI brauchen kein `runAsync`.
- Zeitgeber außerhalb von Widget-Tests (etwa die Steuerung des Abgleichs) prüfen Tests in `fakeAsync` aus `fake_async`, mit `async.getClock(…)` als `clock` des Containers, damit `appClockProvider` und Zeitgeber derselben gestellten Zeit folgen.
- `MockShoppingItemParser` bekommt seine Verzögerung im Konstruktor (in Unit-Tests `Duration.zero`), Widget-Tests lassen die 900 ms des Providers per `tester.pump(Duration)` verstreichen.
- `flutter test` läuft als Android, plattformspezifische Widget-Tests setzen `variant: TargetPlatformVariant.only(...)`, das auch nach Fehlschlägen zurücksetzt.

## Entscheidungen

| Entscheidung | Grund |
| --- | --- |
| Icons und Splash mit `flutter_adaptive_studio` statt `flutter_launcher_icons`, `icons_launcher` oder `flutter_native_splash` | SVG als Quelle mit Safe-Zone-Anpassung, ein 1024er-iOS-Icon samt iOS-18-Varianten, Flavor-Icons samt Xcode-Verdrahtung aus einer Datei. Verworfen (2026-11-21): `flutter_launcher_icons` (seit Juni 2025 kein Release), `icons_launcher` und `flutter_native_splash` (nur PNG). Risiko: junges Paket mit einem Maintainer. |
| `flutter_adaptive_studio` als dev_dependency mit fester Version statt global installiert | Version steht in `pubspec.yaml` und `pubspec.lock` und kommt mit `pub get`, ohne globale Installation, die zudem andere Projekte überschriebe. Dafür lösen seine Abhängigkeiten (`image`, `xml`, `yaml` u. a.) mit denen der App auf. |
| Flavor-Läufe mit `splash: null` und `play_store: false`, Basis mit `round: false` | Flavor-Läufe schrieben sonst den Splash redundant ins Overlay und das Play-Store-Icon nach `src/main` (zuletzt laufender Flavor gewinnt). `round: true` setzt `android:roundIcon` und schreibt dabei das ganze Manifest einzeilig neu, nötig nur für Android 7.1. |
| Flavor per `--flavor` (`appFlavor`) statt `--dart-define` | Ein Schalter für native Konfiguration und Dart, vergessenes `--dart-define` fiele still auf den Standard. |
| `local` über HTTP ohne Ausnahmen in App Transport Security oder Network Security Config | `dart:io` (dios Standard-Adapter) unterliegt keinem, die Engine setzt `may_insecurely_connect_to_all_domains` fest (Stand Flutter 3.50). Ausnahmen erst für nativen HTTP-Stack (WebView, `cupertino_http`, `cronet_http`), nur für `local`. |
| `local` über HTTP statt HTTPS | Verworfen (2026-11-17): bräuchte Aspires Entwicklerzertifikat (experimentelle API) in `auth` und API und Vertrauen in jedem Simulator und Emulator (`dart:io` ignoriert auf Android Nutzer-CAs) und deckte `10.0.2.2` nicht ab. |
| iOS-Configurations nach Flutters Doku dupliziert, `Runner`, `Debug`, `Release`, `Profile` bleiben | Umbenennen oder Löschen bricht `flutter logs` und `flutter create .`, Flutter-Migrationen folgen der Doku. |
| `local` und `development` teilen `de.murmli.app.dev` | CI baut `local` nie, eigene ID kostete App ID und App-Eintrag bei Apple sowie eine Play-Console-App. |
| Android-Emulator über `10.0.2.2` statt `adb reverse` | `adb reverse` geht bei jedem Emulator-Neustart verloren. |
| Keine Timeouts in `apiClientProvider` und `authClientProvider` | API und `auth` skalieren in Dev auf null, ein Timeout müsste den ungemessenen Kaltstart abdecken. Die Anmeldung zeigt bis zur Antwort Fortschritt. Ausnahme ([#126](https://github.com/Murmli/MurmliV2/issues/126)): `SyncCore` bricht jede Anfrage an `/v1/sync` nach 60 s selbst ab, sonst blockierte eine hängende Anfrage alle weiteren Runden; 60 s decken den Kaltstart ab, die Runde endet als `failed` und wird wiederholt. Dafür ein `CancelToken` mit Zeitgeber je Request statt `receiveTimeout`: dio misst `receiveTimeout` nur bis zum ersten und zwischen empfangenen Bytes, `Options` kennt kein `connectTimeout`, und beides wirkt erst im echten Adapter, also nicht in Tests. |
| `local` nur mit E-Mail und Passwort, direkt auf der Onboarding-Seite | Im Simulator ist Sign in with Apple unzuverlässig, Google bräuchte einen Android-Client pro Debug-Schlüssel jedes Entwicklers. Eine eigene Route kostete pro Start einen Tipp. |
| JWT vor Ablauf erneuern und zusätzlich einmal nach 401 wiederholen | Die Erneuerung vor Ablauf spart den abgelehnten Request, die Wiederholung fängt ab, was sie nicht sieht (etwa ein vorzeitig ungültiges JWT). Verworfen: nur eines von beiden. |
| Gültigkeit des JWT ab Empfang zählen | Eine falsch gehende Geräteuhr verschöbe den Vergleich mit `exp`. Verworfen: `exp` gegen die Geräteuhr. |
| JWT nur im Speicher, nur das Session-Token im Secure Storage | Das JWT läuft nach 15 Minuten ab und lässt sich aus der Session jederzeit neu holen. Verworfen: das JWT mitspeichern. |
| Session-Prüfung nach dem Start im Hintergrund | Die App öffnet ohne Netz und ohne auf den Kaltstart von `auth` zu warten, dafür ist bei abgelaufener Session kurz die Startseite sichtbar. Verworfen: im Splash auf die Prüfung warten. |
| Listener in `MurmliApp` führt nach dem Abmelden zur Onboarding-Seite | Greift bei Abmelden, Löschen und abgelaufener Session auf jeder Seite. Verworfen: `reevaluateListenable` von auto_route, es überspringt bereits aufgelöste Guards und wartet auf Animationen. |
| Abmelden nur auf dem Gerät erst nach Bestätigung, wenn `auth` nicht erreichbar ist | Der Nutzer erfährt, dass die Session am Server bis zu 30 Tage weiterläuft, und kann trotzdem abmelden. Verworfen: still nur auf dem Gerät abmelden, Abmelden ohne `auth` verweigern. |
| Installationsmarke leert den Secure Storage nach einer Neuinstallation | Die iOS-Keychain überdauert die Deinstallation. Verworfen: nach einer Neuinstallation auf iOS angemeldet bleiben. |
| Einfacher `Interceptor` mit einer geteilten Erneuerung statt `QueuedInterceptor` | `QueuedInterceptor` reiht alle Requests hintereinander, nicht nur die Erneuerung. |
| Logzeile als Fehler auch bei 401 mit erfolgreicher Wiederholung | Beabsichtigt: `ApiTraceInterceptor` loggt jeden Request vor dem `AccessTokenInterceptor`, so bleibt die Wiederholung im Log sichtbar. Ein Fehlerdialog erscheint nur, wenn auch die Wiederholung scheitert, und dann einmal. |
| Google-Button nach Googles Vorlage statt im Theme-Stil | Die [Branding-Richtlinien](https://developers.google.com/identity/branding-guidelines) schreiben Farben, Schrift und Maße vor. Im Spielraum: Pill wie übrige Buttons statt rechteckig, volle Breite, im Dark Mode „G“ direkt auf dunkler Fläche. Google Sans: offizielle Variable Font aus google/fonts, rund 5 MB, ohne Subsetting. |
| Nur `google_sign_in_android` samt `google_sign_in_platform_interface` statt `google_sign_in` | `google_sign_in` linkte über `google_sign_in_ios` das GoogleSignIn-SDK in die iOS-App (dort nur Apple). Daher direkt `GoogleSignInPlatform.instance`, auf iOS ein nie aufgerufener Platzhalter. Für Google auf iOS ([authentication.md](authentication.md#entscheidungen)) zu `google_sign_in` wechseln, der Test-Fake bleibt. |
| `traceparent` aus eigenem Code statt OpenTelemetry-Bibliothek | Noch kein offizielles OpenTelemetry-SDK für Dart. Spans aus der App: [Murmli/BackOffice#7](https://github.com/Murmli/BackOffice/issues/7). |
| Sampled-Flag `01` | Support-Code führt immer zu einem aufgezeichneten Trace, ohne die API-Sonderregel für `00`. |
| Eigener Interceptor statt `talker_dio_logger` | Loggt (Stand 5.2.0) volle URL samt Query, standardmäßig Bodies, bei Fehlern Header, die Trace-ID nie in Antwort- und Fehler-Logs. |
| Opt-out ohne Einwilligungsdialog, Sitzungen an, Debug-Builds melden nie | [#96](https://github.com/Murmli/MurmliV2/issues/96): Abstürze kommen ohne Zutun an, Crash-free Rate braucht Sitzungen, Entwicklungsfehler gehören nicht in Sentry. |
| Ungesendete Berichte selbst löschen, vor und nach `Sentry.close()` | `sentry_flutter` (Stand 10.5.0) kann gecachte Berichte nicht verwerfen und sendete sie nach dem Wiedereinschalten. Vorher, weil die nativen SDKs beim Beenden bis zu 2 Sekunden senden (iOS alle gecachten), danach, weil sie währenddessen schreiben. Verzeichnisse in `getApplicationCacheDirectory()` laut sentry-java 8.64.0 (`sentry`) und sentry-cocoa 9.35.0 (`io.sentry`, `SentryCrash`). |
| Fehlerdialog global aus `apiClientProvider` statt pro Aufrufer | Jeder fehlgeschlagene Request bekommt ohne Zutun einen Support-Code. |
| `POST /v1/sync` direkt über die Dio-Instanz von `apiClientProvider`, nicht über ein Retrofit-Interface | Der Kern braucht die rohe Antwort: Problem Details nach `type`, `Retry-After`, das Halbieren nach 413, je Request die Ausnahme vom Fehlerdialog und die eigene Zeitgrenze von 60 s. Entschieden, noch nicht gebaut: Retrofit für die übrigen Endpunkte (eigenes Issue). |
| Trace-ID als Tag statt in Sentrys Trace-Kontext | Tags sind durchsuchbar, der Trace-Kontext gehört Sentrys Propagation. |
| Kein `sentry_dio` | Meldet fehlgeschlagene Requests selbst, setzt Trace-Header (`sentry-trace`, `baggage`), schreibt Breadcrumbs mit voller URL. |
| `print`- und HTTP-Breadcrumbs aus, Screenshots und View Hierarchy beim Standard (aus) | `print`-Breadcrumbs enthielten Talkers Request-Logs von der Konsole, HTTP-Breadcrumbs die volle URL. |
| `local-data` schon jetzt aus den Sicherungen des Systems | Die Daten gehören zum angemeldeten Konto, eine Wiederherstellung auf einem anderen Gerät oder nach dem Abmelden brächte fremde oder veraltete Daten zurück. Mit dem Abgleich kommen sie ohnehin vom Server. |
| Downgrade der lokalen Datenbank legt alle Tabellen neu an | Ein Downgrade kommt nur beim Wechsel auf einen älteren Build vor, eine Rückwärts-Migration je Version wäre Aufwand ohne Nutzen. Die abgeglichenen Daten holt der nächste Abgleich vom Server, verloren gehen nur noch nicht gesendete Kommandos. Auch der älteren Version unbekannte Tabellen fallen weg, sonst scheiterte ein späteres Upgrade, das sie wieder anlegt. |
| Beispieldaten nur in Debug-Builds und im Flavor `local` | Release-Builds von `development` und `production` starten mit leerer Liste wie später mit dem Abgleich. |
| Kategorie-Reihenfolge und Rezeptanteile in eigenen lokalen Tabellen statt als Felder von Liste oder Artikel | Beide bleiben vorerst lokal (Reihenfolge je Person, Rezeptanteile bis zum Übernehmen von Rezeptzutaten), die abgeglichenen Tabellen behalten die Form des Abgleichs. |
| Bottom Sheets der Einkaufsliste (Artikelmenü, Bearbeiten, Optionsmenü) auf dem Root-Navigator (`useRootNavigator: true`) | Sie liegen über der Navigationsleiste der Startseite statt darunter. |
| Artikelmenü aus dem Design statt der früheren Schnellbearbeitung (Name, Menge und Kategorie direkt nach dem Tap) | Entscheidung des Nutzers (2026-11-28, [#181](https://github.com/Murmli/MurmliV2/issues/181)): Das Menü bündelt die Aktionen auf einem Artikel, Bearbeiten bleibt per langem Druck direkt erreichbar. |
| Löschen eines Artikels ohne Nachfrage, Rückgängig zurückgestellt | Entscheidung des Nutzers (2026-11-28): Löschen soll schnell gehen, ein Rückgängig kommt erst später. |
| Modelle nur mit dart_mappable, nicht freezed | Ein Generator für Gleichheit, `copyWith` und Serialisierung. Verworfen (2026-11-27): freezed daneben. |
| Kategorie-Icons als eigene SVG-Assets (flutter_svg) statt Material-Icons | Ein einheitliches Set aus dem Design für alle 22 Kategorien (24er-Raster, Strich 2, runde Enden), gefärbt über die Farbfamilie der Kategorie per `ColorFilter`. |
