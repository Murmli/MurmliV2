# App

Die Flutter-App liegt in `src/app` (Pfade unten relativ dazu), die Flutter-Version steht in `src/app/.fvmrc`, Befehle laufen mit `fvm`.

## Flavors

Die App hat die Flavors `local`, `development` und `production`. `pubspec.yaml` setzt unter `flutter:` `default-flavor: development`, jeder `flutter`-Befehl ohne `--flavor` (`run`, `build`, `test`) nutzt deshalb `development`. Auf beiden Plattformen teilen `development` und `local` die ID `de.murmli.app.dev` (Bundle-ID auf iOS, App-ID auf Android) und den Namen „Murmli Dev“, `production` hat `de.murmli.app` und „Murmli“. Den Namen setzt auf iOS das Build-Setting `APP_DISPLAY_NAME` pro Configuration, auf Android der Manifest-Platzhalter `appLabel` pro Flavor. `development` und `local` lassen sich deshalb nicht nebeneinander installieren, `production` neben ihnen schon.

- `lib/app/core/flavor/flavor.dart`: Enum `Flavor` mit dem Text des Banners (`local`, `dev`, für `production` keiner).
- `lib/app/core/flavor/flavor_provider.dart`: `flavorProvider` liest `appFlavor`, eine Compile-Zeit-Konstante aus `package:flutter/services.dart`, gesetzt per `--flavor` oder `default-flavor`.
- `lib/app/core/flavor/app_endpoints.dart`: `AppEndpoints` mit den Adressen von API und `auth` pro Flavor. `app_endpoints_provider.dart` stellt sie als `appEndpointsProvider` bereit.

| Flavor | API | Anmeldung (`auth`) |
| --- | --- | --- |
| `local` | `http://localhost:5020` (iOS-Simulator), `http://10.0.2.2:5020` (Android-Emulator) | `http://localhost:5021` (iOS-Simulator), `http://10.0.2.2:5021` (Android-Emulator) |
| `development` | `https://api.kinddune-9cab4a57.francecentral.azurecontainerapps.io` | `https://auth.kinddune-9cab4a57.francecentral.azurecontainerapps.io` |
| `production` | noch keine | noch keine |

- `local` braucht ein laufendes `aspire run` (Voraussetzungen in [AGENTS.md](../AGENTS.md#aspire-und-azure)). Der Port der API kommt aus ihrem Launch-Profil, der von `auth` steht fest in `AddAuth()`. `10.0.2.2` ist der Alias des Android-Emulators für das Loopback des Hosts.
- `local` funktioniert nur im Simulator bzw. Emulator, auf echten Geräten gegen `development` testen.
- Ab targetSdk 37 (Android 17) braucht `local` Androids Berechtigung für das lokale Netzwerk, um `10.0.2.2` zu erreichen ([Local network permission](https://developer.android.com/privacy-and-security/local-network-permission)). Heute nutzt die App Flutters Standard-targetSdk 36.
- `development` nutzt die Standard-Domain der Container-Apps-Umgebung. Wird die Umgebung neu angelegt, ändert sich die Domain, dann `AppEndpoints` und diese Doku anpassen.
- `production` hat bis zum Release keine Adressen, sie zu lesen wirft `UnimplementedError`. Eine Prüfung beim Start oder Build gibt es bewusst nicht. Dieser Hinweis entfällt, sobald es mit dem Release Werte für `production` gibt.
- `lib/app/core/widgets/flavor_banner.dart`: `FlavorBanner` legt per `MaterialApp.router(builder: ...)` Flutters `Banner` oben links über die App, mit dem Text `local` bzw. `dev`, in `production` nichts.

## Starten und Bauen

In `src/app`:

```bash
fvm flutter run --flavor local
fvm flutter run # development
fvm flutter run --flavor production
fvm flutter build appbundle --flavor development
fvm flutter build ios --flavor development --no-codesign
```

- In Android Studio und IntelliJ starten die geteilten Run-Configurations `App (Flavor: local)`, `App (Flavor: development)` und `App (Flavor: production)` in `.idea/runConfigurations` die App mit dem jeweiligen Flavor.
- Die App per `flutter` starten. Aus Xcode tragen nur die Schemes `local`, `development` und `production` einen Flavor (Flutter liest ihn aus der Configuration), das Scheme `Runner` nicht: Dort käme `appFlavor` aus dem, was die CLI zuletzt in `ios/Flutter/Generated.xcconfig` geschrieben hat, meist ist er leer und `flavorProvider` bricht beim Start mit einem `StateError` ab.
- Android: `productFlavors` `local`, `development` und `production` mit der Dimension `environment` in `android/app/build.gradle.kts`. `local` und `development` setzen `applicationIdSuffix` `.dev`, jeder Flavor setzt `manifestPlaceholders["appLabel"]`, aus dem `android/app/src/main/AndroidManifest.xml` `android:label` liest. Signieren von Release-Builds in [google-play.md](google-play.md#build-in-der-ci).
- iOS: pro Flavor die Build-Configurations `Debug-<flavor>`, `Release-<flavor>` und `Profile-<flavor>` (Kopien von `Debug`, `Release` und `Profile`, wie es Flutters Doku zu Flavors auf iOS vorgibt) und ein geteiltes Scheme `<flavor>` (Kopie von `Runner.xcscheme` samt der Pre-Action „Run Prepare Flutter Framework Script“ und der LLDB-Init-Datei). `Runner.xcscheme` und die einfachen Configurations `Debug`, `Release` und `Profile` bleiben. Jede Configuration des Targets `Runner` setzt `PRODUCT_BUNDLE_IDENTIFIER` und `APP_DISPLAY_NAME`, aus dem `Info.plist` `CFBundleDisplayName` liest.
- Das Xcode-Projekt enthält kein `DEVELOPMENT_TEAM`: Im Simulator braucht die App kein Team, für ein Gerät das Team lokal in Xcode wählen und nicht committen. Team und manuelles Signieren setzt die CI nur auf dem Runner ([apple.md](apple.md#build-in-der-ci)).
- Flavor-Namen sind klein und ohne `-`: Flutter leitet den Flavor auf iOS aus dem Teil nach dem `-` im Namen der Configuration ab, und `flavorProvider` bildet den Namen per `byName` exakt auf das Enum `Flavor` ab.
- Das Projekt nutzt nur Swift Package Manager. Braucht ein Plugin einmal CocoaPods, muss das Podfile die Flavor-Configurations zuordnen (`'Debug-local' => :debug`, `'Profile-local' => :release`, `'Release-local' => :release`, ebenso für die anderen Flavors).

## API-Zugriff

- `lib/app/core/api/api_client_provider.dart`: `apiClientProvider` liefert die gemeinsame `Dio`-Instanz für die eigene API, mit der Adresse der API aus `appEndpointsProvider` als `baseUrl` und dios Standard-Adapter (`dart:io`). Noch ruft kein App-Code die API auf, der erste Aufruf kommt mit der Anmeldung ([#53](https://github.com/Murmli/MurmliV2/issues/53)). Dieser Satz entfällt mit [#53](https://github.com/Murmli/MurmliV2/issues/53).
- Requests nennen nur den Pfad ab `/` (`/v1/...`), nie eine volle URL. dio hängt den Pfad als Text an die `baseUrl`, die ohne `/` endet: Ohne führenden `/` entstünde eine ungültige Adresse (bei `development` ein falscher Host, bei `local` ein ungültiger Port). Eine volle URL ignoriert die `baseUrl`. Code, der nur Requests an die eigene API betreffen darf, vergleicht deshalb die `origin` von `RequestOptions.uri` mit der von `appEndpointsProvider` und verlässt sich nicht auf die Instanz.
- `lib/app/core/api/api_trace_interceptor.dart`: `ApiTraceInterceptor` gibt jedem Request an die eigene API (gleiche `origin` wie die API aus `appEndpointsProvider`) einen neuen W3C-`traceparent` mit: `00-<Trace-ID>-<Parent-ID>-01`, 16 bzw. 8 Byte aus `Random.secure()` als Hex in Kleinbuchstaben, nie nur Nullen. Requests an andere Ziele (`auth`, Drittanbieter) bekommen keinen, auch wenn sie über dieselbe Instanz laufen. Die API setzt den Trace fort und zeichnet ihn unabhängig vom Sampled-Flag auf ([telemetry.md](telemetry.md#entscheidungen)).
- Pro Request an die eigene API schreibt `ApiTraceInterceptor`, wenn er endet, einen Eintrag über `talkerProvider` (`lib/app/core/logging/talker_provider.dart`, der Talker aus `main.dart`): Methode, Pfad ohne Query, Statuscode bzw. Fehlertyp (`DioExceptionType`), Dauer und Trace-ID, Fehler auf Level `error`, Antworten und Abbrüche auf `info`. Nie Bodies, Header oder Query: Bodies können Gesundheitsdaten enthalten, Header tragen mit [#54](https://github.com/Murmli/MurmliV2/issues/54) das Token. Die `DioException` hängt `ApiTraceInterceptor` nicht an den Eintrag, ihren Text (`toString()`) ersetzt er durch dieselben Angaben: `main.dart` loggt unbehandelte Fehler mit ihrem Text, Sentry meldet sie mit ihm ([Absturzberichte](#absturzberichte-sentry)), und dios Standardtext enthält ihren `error`, etwa eine `HttpException` mit der vollen URL samt Query oder eine `FormatException` mit Teilen des Bodies.
- Schlägt ein Request an die eigene API fehl (jede `DioException` außer einem Abbruch per `CancelToken`), meldet `apiClientProvider` die Trace-ID an `failedApiRequestTraceIdProvider`. `ApiErrorDialogListener` (`lib/app/core/widgets/api_error_dialog_listener.dart`, im `builder` von `MaterialApp.router`) zeigt daraufhin über den Navigator des `AppRouter` einen Fehlerdialog mit der Trace-ID als Support-Code, über den sich der Request im Backend findet. Höchstens ein Dialog gleichzeitig, weitere Fehler währenddessen stehen nur im Log. Kein Dialog, solange die App nicht sichtbar ist (`hidden`, `paused`, `detached`) oder der Navigator fehlt, auch nicht nachträglich. Der Fehler geht trotzdem an den Aufrufer, Aufrufer zeigen dafür keinen eigenen Dialog.
- Reihenfolge in `apiClientProvider`: `ApiTraceInterceptor` zuerst, die Meldung an `failedApiRequestTraceIdProvider` zuletzt. dio ruft auch `onError` in dieser Reihenfolge auf, `handler.resolve` überspringt die folgenden. Ein Interceptor, der Fehler selbst behandelt (etwa die Token-Erneuerung aus [#54](https://github.com/Murmli/MurmliV2/issues/54)), kommt dazwischen: So bleibt jeder Request im Log, und ein selbst behobener Fehler löst keinen Dialog aus.
- Android-Release-Builds dürfen per `android.permission.INTERNET` in `android/app/src/main/AndroidManifest.xml` ins Netz. Die gleichen Einträge in den Manifesten unter `debug` und `profile` stammen aus Flutters Vorlage und bleiben.

## Absturzberichte (Sentry)

- `sentry_flutter` meldet unbehandelte Dart-Fehler (`FlutterError.onError`, `PlatformDispatcher.onError`), native Abstürze, ANRs (Android) und App Hangs (iOS) an Sentry: Organisation `murmli` in der EU-Region (`de.sentry.io`), Projekt `app`. Nur Release- und Profile-Builds von `development` und `production` melden, mit dem Flavor-Namen als Environment. In `local` und in Debug-Builds startet Sentry nicht: `CrashReporting` prüft neben dem Flavor `debugBuildProvider` (`lib/app/core/build_mode/debug_build_provider.dart`), der `kDebugMode` liest, wie `appFlavor` eine Compile-Zeit-Konstante. Der DSN steht pro Flavor im Switch in `lib/app/core/crash_reporting/crash_reporting_provider.dart`, ein DSN ist kein Geheimnis.
- Standard ist an (Opt-out). Das Onboarding weist unter dem Hinweis zu AGB und Datenschutzerklärung darauf hin, in den Einstellungen schaltet „Fehlerberichte senden“ im Bereich „Datenschutz“ (`CrashReportingSection`) das Melden aus und wieder ein. Die Wahl steht in den SharedPreferences unter `crash_reporting_enabled`.
- `CrashReporting` (`crash_reporting_provider.dart`) hält die Wahl und entscheidet nach Flavor und Build-Modus, `CrashReporter` (`crash_reporter.dart`, über `crashReporterProvider`) spricht als einziger Code mit dem SDK. `main.dart` ruft `CrashReporting.start()` nach dem Setzen der Talker-Handler und dem Laden der SharedPreferences auf, vor `runApp`. Fehler davor meldet Sentry nicht.
- `SentryFlutter.init` legt seine Handler vor die aus `main.dart` und ruft diese weiter auf, Talker loggt also unverändert. `Sentry.close()` setzt die Handler aus `main.dart` zurück.
- Ausschalten speichert die Wahl, beendet Sentry samt nativen SDKs sofort (`Sentry.close()`) und löscht davor und danach die ungesendeten Berichte der nativen SDKs im Cache-Verzeichnis der App (`getApplicationCacheDirectory()`): `sentry` (Android), `io.sentry` und `SentryCrash` (iOS). Davor, weil die nativen SDKs beim Beenden bis zu 2 Sekunden lang senden, das iOS-SDK dabei alle zwischengespeicherten Berichte; danach, weil sie beim Beenden noch Berichte schreiben. Einschalten startet Sentry sofort wieder. Jeder Wechsel wartet auf den vorigen, damit schnelles Aus- und Einschalten nicht den Cache des neu gestarteten SDK löscht.
- Nach dem Wiedereinschalten meldet das Android-SDK den letzten ANR der vergangenen 90 Tage aus der Systemhistorie (`ApplicationExitInfo`), auch wenn er in die Zeit ohne Meldungen fiel oder schon gemeldet war: Die Marke des zuletzt gemeldeten ANR lag im gelöschten Cache.
- Ein Ereignis enthält Typ und Text (`toString()`) des Fehlers, den Stacktrace, bei Fehlern aus `FlutterError.onError` zusätzlich `flutter_error_details` mit Kontext und Diagnose der `FlutterErrorDetails` (etwa `NetworkImage("<URL>")` mit voller URL, wenn ein Bild nicht lädt), Gerät, Betriebssystem, Release (`<Bundle-ID bzw. App-ID>@<Version>+<Build>`, bei `development` auf beiden Plattformen mit `de.murmli.app.dev`), Environment und die automatischen Breadcrumbs der nativen SDKs (etwa App-Lebenszyklus und Systemereignisse). Ereignisse und Sitzungen tragen die zufällige Installations-ID der nativen SDKs (Android und iOS) als Nutzer- bzw. Distinct-ID, die Konto-ID als Nutzer kommt mit [#53](https://github.com/Murmli/MurmliV2/issues/53), [#54](https://github.com/Murmli/MurmliV2/issues/54) und [#55](https://github.com/Murmli/MurmliV2/issues/55).
- Sentry zählt Sitzungen (Release Health, Standard des SDK) für den Anteil absturzfreier Sitzungen (Crash-free Rate): Solange das Melden an ist, beginnt bei jedem Start von Sentry (App-Start, Wiedereinschalten) und bei jeder Rückkehr aus mindestens 30 Sekunden im Hintergrund (Standard von `autoSessionTrackingInterval`) eine Sitzung, deren Beginn und Ende an Sentry gehen, auch ohne Fehler.
- Stammt der Fehler aus einem Request an die eigene API (`DioException` mit Trace-ID, auch in Riverpods `ProviderException` verpackt), setzt `ApiTraceIdEventProcessor` (`lib/app/core/crash_reporting/api_trace_id_event_processor.dart`) das Tag `api_trace_id` auf dessen Trace-ID. Die Suche `api_trace_id:<Support-Code>` findet in Sentry das Ereignis zum Support-Code aus dem Fehlerdialog.
- Bewusst aus (in `configureCrashReporting` in `lib/app/core/crash_reporting/crash_reporting_options.dart` oder per Standard des SDK): fehlgeschlagene HTTP-Requests als eigene Meldungen (`captureFailedRequests`), Trace-Header von Sentry (`tracePropagationTargets` leer, einziger Trace-Header bleibt der eigene `traceparent`), App-Logs, `print`- und `debugPrint`-Breadcrumbs (`enablePrintBreadcrumbs`, Talker schreibt die Request-Logs mit Pfad und Trace-ID auf die Konsole), HTTP-Breadcrumbs mit voller URL (`recordHttpBreadcrumbs`), Client Reports mit der Zahl verworfener Ereignisse (`sendClientReports`), Session Replay und Performance-Tracing (keine Sample-Raten), Screenshots, View Hierarchy und `sendDefaultPii`.
- Debug-Symbole und R8-Mappings lädt nur die CI hoch ([ci.md](ci.md#app)).

## Tests

- `test/app/core/flavor/flavor_provider_test.dart` deckt den Standard-Flavor ab und verlässt sich darauf, dass `flutter test` ohne `--flavor` läuft.
- `appFlavor` und `kDebugMode` sind Compile-Zeit-Konstanten, Tests setzen den Flavor deshalb über `pumpApp(tester, flavor: ...)` bzw. `createContainer(preferences, flavor: ...)` und den Build-Modus über `createContainer(preferences, debugBuild: ...)`. `flutter test` läuft im Debug-Modus, in dem Sentry nie startet: Tests von `CrashReporting` setzen `debugBuild` deshalb ausdrücklich, sonst bliebe der Start auch ohne den geprüften Grund aus.
- Kein Test spricht mit einer echten API: Tests ersetzen `httpClientAdapter` der Instanz aus `apiClientProvider` durch `RecordingHttpClientAdapter` aus `test/helpers/http_client_adapter.dart`. Ausnahme ist der Test, dass Requests keine Trace-Header von Sentry tragen: Header, die eine Sentry-Integration wie `sentry_dio` im Adapter setzt, sähe `RecordingHttpClientAdapter` nicht. Er behält dios echten Adapter und leitet den Request per `HttpOverrides` als Proxy an einen `HttpServer` auf Loopback.
- `createContainer` (und damit `pumpApp`) überschreibt `talkerProvider` mit einem Talker ohne Konsolenausgabe, Tests prüfen Logs über dessen `history`.
- `createContainer` (und damit `pumpApp`) ersetzt `crashReporterProvider` durch `RecordingCrashReporter` (`test/helpers/crash_reporter.dart`), der Starts und Stopps nur aufzeichnet, kein Test startet die nativen SDKs. Tests, die prüfen, was an Sentry geht, starten Sentry mit `startRecordingSentry` (`test/helpers/sentry.dart`) rein in Dart (`Sentry.init`) mit einem Transport, der Envelopes aufzeichnet, mit Standardoptionen oder per `configure` etwa mit `configureCrashReporting`.
- Widget-Tests hängen die Erwartung an einen Request per `expectLater` vor `tester.pumpAndSettle()` an und warten erst danach auf sie: dio arbeitet über Timer, die unter `FakeAsync` nur beim Pumpen laufen. Direkt gewartet hängt der Test, eine erst nach dem Pumpen angehängte Erwartung meldet den Fehler als unbehandelt.

## Entscheidungen

| Entscheidung | Grund |
| --- | --- |
| Flavor aus `appFlavor` (per `--flavor` oder `default-flavor`) statt `--dart-define` | Ein Schalter für native Konfiguration und Dart, keine Argumente neben `--flavor` in Befehlen, IDE und CI. Ein vergessenes `--dart-define` fiele still auf einen Standardwert zurück. |
| `local` über HTTP ohne Ausnahmen in App Transport Security oder Androids Network Security Config | Die App spricht über `dart:io` (Standard-Adapter von dio), das in Flutter keinem von beiden unterliegt: Die Engine setzt `may_insecurely_connect_to_all_domains` fest (Stand Flutter 3.50). Ausnahmen werden erst nötig, wenn lokaler Verkehr über einen nativen HTTP-Stack läuft (WebView, `cupertino_http`, `cronet_http`), und dann nur für `local`. |
| `local` über HTTP statt HTTPS | Geprüft und verworfen (2026-11-17): HTTPS bräuchte TLS in `auth` und der API über Aspires Entwicklerzertifikat (experimentelle API), Vertrauen in jedem Simulator und Emulator pro Entwickler (`dart:io` ignoriert auf Android vom Nutzer installierte CAs), und das Entwicklerzertifikat deckt `10.0.2.2` nicht ab. |
| iOS-Configurations wie in Flutters Doku dupliziert, `Runner` bleibt | Umbenannte Configurations und ein gelöschtes `Runner` brechen `flutter logs` und `flutter create .` und weichen von der Doku ab, der künftige Flutter-Migrationen folgen. |
| `local` und `development` teilen `de.murmli.app.dev` | Die Pipeline baut `local` nie, eine eigene ID kostete nur eine App ID und einen App-Eintrag bei Apple und eine App in der Play Console ohne Nutzen. |
| Kein Abbruch für `production` beim Start oder Build | Die Werte für `production` kommen mit dem Release, bis dahin wirft nur das Lesen der Adressen. |
| Android-Emulator über `10.0.2.2` statt `adb reverse` | `adb reverse` geht bei jedem Neustart des Emulators verloren. |
| Keine Timeouts in `apiClientProvider` | dio setzt standardmäßig keine. Die API skaliert in Dev auf null, ein Timeout für die Antwort müsste deren Kaltstart abdecken, und ohne Aufrufer gibt es keinen Endpunkt, an dem sich ein Wert messen ließe. Die Werte legt der erste Aufrufer fest, dann entfällt diese Zeile. |
| `traceparent` aus eigenem Code statt einer OpenTelemetry-Bibliothek | Ein offizielles OpenTelemetry-SDK für Dart gibt es noch nicht, für einen Header reicht eigener Code. Spans aus der App gehören zu [Murmli/BackOffice#7](https://github.com/Murmli/BackOffice/issues/7). |
| Sampled-Flag `01` | Der Support-Code soll immer auf einen aufgezeichneten Trace führen. Die API zeichnet zwar auch bei `00` auf, mit `01` hängt das aber nicht an dieser Sonderregel. |
| Eigener Interceptor statt `talker_dio_logger` | `talker_dio_logger` (Stand 5.2.0) loggt die volle URL samt Query, standardmäßig Request- und Antwort-Bodies und bei Fehlern die Header. Die Trace-ID stünde nur über `printRequestExtra` (alle Extras) im Request-Log, nie in Antwort- und Fehler-Logs. |
| Fehlerdialog global aus `apiClientProvider` statt pro Aufrufer | Jeder fehlgeschlagene Request bekommt einen Support-Code, ohne dass ein Aufrufer daran denken muss. Ein Abbruch per `CancelToken` ist kein Fehler, für den Nutzer einen Support-Code brauchen. |
| Logs ohne Query | Query-Werte sind Nutzereingaben (etwa Suchbegriffe). Pfad und Trace-ID reichen, den vollen Request kennt das Backend. |
| Opt-out mit Hinweis im Onboarding und Schalter in den Einstellungen, ohne Einwilligungsdialog | Festgelegt in [#96](https://github.com/Murmli/MurmliV2/issues/96): Abstürze sollen ohne Zutun ankommen, Hinweis und Schalter machen das Melden sichtbar und abschaltbar. |
| Ungesendete Berichte selbst löschen | `sentry_flutter` (Stand 10.5.0) hat keine API, die gecachte Berichte verwirft, ohne Löschen sendete das SDK sie nach dem Wiedereinschalten. Die Verzeichnisnamen stammen aus sentry-java 8.64.0 (`<Cache>/sentry`) und sentry-cocoa 9.35.0 (`<Caches>/io.sentry`, `<Caches>/SentryCrash`), bei Updates von `sentry_flutter` prüfen. |
| Trace-ID als Tag statt im Trace-Kontext von Sentry | Tags sind durchsuchbar, der Trace-Kontext gehört Sentrys eigener Propagation. |
| Kein `sentry_dio` | Es meldet fehlgeschlagene Requests selbst, setzt eigene Trace-Header (`sentry-trace`, `baggage`) und schreibt Breadcrumbs mit voller URL. |
| Sitzungen (Release Health) an | Festgelegt in [#96](https://github.com/Murmli/MurmliV2/issues/96): Die Crash-free Rate braucht Sitzungen, dafür gehen auch ohne Fehler Sitzungen an Sentry. |
| Debug-Builds melden nie, auch nicht mit `development` | Festgelegt in [#96](https://github.com/Murmli/MurmliV2/issues/96): Beim Entwickeln ausgelöste Fehler gehören nicht in Sentry. Der Build-Modus kommt aus `debugBuildProvider` statt direkt aus `kDebugMode`, weil `flutter test` immer im Debug-Modus läuft und Tests den Start sonst nicht prüfen könnten. |
